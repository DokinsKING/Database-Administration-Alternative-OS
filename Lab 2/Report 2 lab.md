## 1. Утилиты резервного копирования: pg_dump и pg_basebackup

### 1.1 pg_dump (логическое резервное копирование)
`pg_dump` создаёт **логическую** копию базы данных: DDL (схемы/таблицы/функции/права) и данные (INSERT/COPY).  
Поддерживает **выборочное копирование** (схема/таблица/только данные/только структура).

**Сценарии применения:**
- регулярные бэкапы одной базы или отдельных схем/таблиц;
- перенос данных между серверами/версиями PostgreSQL;
- частичное восстановление (например, только одну таблицу).

### 1.2 pg_basebackup (физическое резервное копирование)
`pg_basebackup` делает **физическую** копию всего кластера PostgreSQL (каталога данных).  
Обычно используется для репликации и для аварийного восстановления “как было”, особенно вместе с WAL (PITR).

**Сценарии применения:**
- создание реплики (streaming replication);
- восстановление всего сервера/кластера;
- PITR (восстановление до момента времени) при наличии WAL.

**Ключевое отличие:** `pg_dump` — “логика (SQL-объекты)”, `pg_basebackup` — “файлы кластера”.

## 2. Создание полной резервной копии базы (pg_dump)

### 2.1 Подготовка каталога для бэкапов
Создан каталог для хранения резервных копий и выставлены права доступа:

```bash
sudo mkdir -p /var/backups/postgresql
sudo chown -R postgres:postgres /var/backups/postgresql
sudo chmod 750 /var/backups/postgresql
```

**Пояснение:**
- `/var/backups/postgresql` — выделенное место под бэкапы;
- владелец `postgres` нужен, чтобы команда `pg_dump`, выполняемая от имени `postgres`, могла записывать файлы;
- `750` ограничивает доступ посторонним пользователям (в бэкапах содержатся данные).

### 2.2 Переход под системного пользователя postgres
```bash
sudo -i -u postgres
```

В Debian сервис PostgreSQL обычно работает от имени пользователя ОС `postgres`. Под ним удобно выполнять локальные операции (часто без запроса пароля при socket/peer auth).

### 2.3 Полный бэкап базы в формате `-Fc` (custom)
```bash
pg_dump -p 5445 -U postgres -Fc -d velbd \
  -f /var/backups/postgresql/velbd_full_$(date +%F).dump
```

**Пояснение параметров:**
- `-p 5445` — порт сервера PostgreSQL;
- `-U postgres` — роль БД, от имени которой выполняется бэкап;
- `-d velbd` — имя базы данных;
- `-Fc` — формат **custom** (архивный, предназначен для `pg_restore`);
- `-f ...` — путь к файлу результата.

### 2.4 Форматы `-Fc` и `-Ft` — разница
- `-Fc` (**custom**) — компактный архив, удобен для `pg_restore`, поддерживает выборочное восстановление и параллельность (`-j`).
- `-Ft` (**tar**) — tar-архив, также восстанавливается через `pg_restore`, иногда удобен для “архивного” хранения.

## 3. Частичное (выборочное) резервное копирование

### 3.1 Дамп только схемы `test_schema`
```bash
pg_dump -p 5445 -Fc -d velbd -n test_schema \
  -f /var/backups/postgresql/velbd_test_schema_$(date +%F).dump
```

**Пояснение:**
- `-n test_schema` означает “включить в дамп только эту схему” (с объектами и данными внутри неё).

### 3.2 Дамп только выбранной таблицы
Был выполнен дамп таблицы `test_schema.clothes`:

```bash
pg_dump -p 5445 -Fc -d velbd -t test_schema.clothes \
  -f /var/backups/postgresql/velbd_public_tables_$(date +%F).dump
```

**Пояснение:**
- `-t schema.table` позволяет сохранять **конкретные таблицы**.
- В данном случае таблица находится в `test_schema` (а не в `public`), при этом имя файла содержит `public_tables` — для отчёта важно отметить, что название файла можно выбрать произвольное, но корректнее называть по факту (например `velbd_test_schema_clothes_YYYY-MM-DD.dump`).

### 3.3 Отличие от бэкапа всей базы
- **Полный бэкап** включает все схемы/таблицы/данные/объекты базы.
- **Частичный бэкап** меньше по размеру и быстрее, но может не включать зависимости (типы/функции/связи), если они находятся вне выбранной схемы/таблиц.

## 4. Восстановление из резервной копии

### 4.1 Создание базы для восстановления
```bash
createdb -p 5445 -O Vel velbd_restore
```

**Пояснение:** восстановление выполняется в отдельную базу `velbd_restore`, чтобы не повредить исходную `velbd`.  
Параметр `-O Vel` назначает владельца базы.

### 4.2 Восстановление из custom-архива через pg_restore
```bash
pg_restore -p 5445 -d velbd_restore \
  /var/backups/postgresql/velbd_full_2026-02-14.dump
```

**Пояснение:**
- `pg_restore` применяется для архивных форматов (`-Fc`, `-Ft`, `-Fd`).
- `-d velbd_restore` — куда восстанавливать.

### 4.3 Проверка результата восстановления
```bash
psql -h 127.0.0.1 -p 5445 -U Vel -d velbd_restore -c "\dt"
```

 `\dt` выводит список таблиц (проверка, что структура восстановилась).

## 5. Автоматизация бэкапов с помощью cron + ротация

### 5.1 Создание скрипта бэкапа
Создан файл:

```bash
sudo nano /usr/local/bin/pg_backup_velbd.sh
```

Содержимое скрипта:

```bash
#!/usr/bin/env bash
set -euo pipefail

HOST="127.0.0.1"
PORT="5445"
DB="velbd"
USER="postgres"
BACKUP_DIR="/var/backups/postgresql"
KEEP_DAYS=7

DATE="$(date +%F)"
FILE="${BACKUP_DIR}/${DB}_full_${DATE}.dump"

# дамп в custom-формате
pg_dump -p "$PORT" -U "$USER" -Fc -d "$DB" -f "$FILE"

# ротация: удалить файлы старше KEEP_DAYS
find "$BACKUP_DIR" -type f -name "${DB}_full_*.dump" -mtime +"$KEEP_DAYS" -delete
```

**Пояснение важного:**
- `set -euo pipefail` — безопасный режим bash: остановка при ошибках/неопределённых переменных.
- `KEEP_DAYS=7` — хранить бэкапы 7 дней.
- `find ... -mtime +7 -delete` — **ротация**: удаление файлов старше 7 суток.
- Внутри скрипта `pg_dump` вызывается без `sudo`, так как скрипт запускается от имени `postgres`.

### 5.2 Выставление прав на выполнение
```bash
sudo chmod +x /usr/local/bin/pg_backup_velbd.sh
```

### 5.3 Тестовый запуск от имени postgres
```bash
sudo -i -u postgres
/usr/local/bin/pg_backup_velbd.sh
ls -lh /var/backups/postgresql
```

### 5.4 Настройка cron
Открытие crontab для пользователя `postgres`:

```bash
crontab -e
```

Добавлено ежедневное задание (02:10):

```cron
10 2 * * * /usr/local/bin/pg_backup_velbd.sh >> /var/log/pg_backup_velbd.log 2>&1
```

**Пояснение:**
- `10 2 * * *` — каждый день в 02:10.
- `>> ... 2>&1` — логирование stdout и stderr в файл.

**Замечание по правам:** пользователь `postgres` часто не имеет прав записи в `/var/log`.  
Практичный вариант — писать лог в каталог бэкапов, например:

```cron
10 2 * * * /usr/local/bin/pg_backup_velbd.sh >> /var/backups/postgresql/pg_backup_velbd.log 2>&1
```

## 6. Мониторинг состояния системы (Debian)

Для мониторинга потребления ресурсов PostgreSQL использовались стандартные инструменты ОС.

### 6.1 top / htop (CPU и память)
- `top`/`htop` показывают процессы PostgreSQL и их нагрузку:
  - **%CPU** — использование процессора;
  - **RES** — реально занятая оперативная память;
  - **VIRT** — виртуальная память (не равно фактически используемой);
  - состояние процесса (R/S/D и т.д.).

### 6.2 iotop (дисковый ввод/вывод)
- `iotop` показывает, какие процессы активно читают/пишут на диск:
  - **DISK READ/WRITE** — скорость чтения/записи;
  - полезно при поиске “узкого места” по диску.

## 7. Мониторинг PostgreSQL (встроенная статистика)

Подключение к базе:

```bash
psql -h 127.0.0.1 -p 5445 -U Vel -d velbd
```

### 7.1 Просмотр активных сессий и запросов (pg_stat_activity)
```sql
SELECT pid, usename, datname, client_addr, state, wait_event_type, wait_event,
       now() - query_start AS running_for,
       left(query, 120) AS query
FROM pg_stat_activity
WHERE datname = 'velbd'
ORDER BY running_for DESC;
```

**Пояснение:**
- `pid` — идентификатор серверного процесса (нужен для остановки);
- `state` — состояние (active/idle/и т.д.);
- `running_for` — сколько времени выполняется запрос;
- `wait_event_*` — чего ждёт процесс (локи/IO/и т.д.).

### 7.2 Поиск “долгих” запросов
```sql
SELECT pid, usename, now() - query_start AS running_for, state,
       left(query, 200) AS query
FROM pg_stat_activity
WHERE state = 'active'
  AND now() - query_start > interval '30 seconds'
ORDER BY running_for DESC;
```

**Пояснение:** позволяет выделить запросы, работающие дольше заданного порога.

### 7.3 Принудительное завершение запроса/сессии (нужен суперпользователь)
Мягкая остановка (отмена текущего запроса):
```sql
SELECT pg_cancel_backend(<pid>);
```

Жёсткая остановка (разорвать соединение):
```sql
SELECT pg_terminate_backend(<pid>);
```

## 8. Логирование и анализ логов

### 8.1 Логи PostgreSQL (systemd)
Просмотр последних сообщений сервиса PostgreSQL:

```bash
sudo journalctl -u postgresql --no-pager -n 200
```

**Что можно увидеть:** старт/остановка сервиса, ошибки, предупреждения, сообщения конфигурации.

### 8.2 Файловые логи PostgreSQL
```bash
sudo ls -lah /var/log/postgresql/
sudo tail -n 200 /var/log/postgresql/postgresql-*.log
```

**Что логируется СУБД:** ошибки SQL, ошибки аутентификации, события сервера (в зависимости от настроек `postgresql.conf`).

### 8.3 Системные логи Debian
```bash
sudo ls -lah /var/log/
sudo tail -n 200 /var/log/syslog
sudo tail -n 200 /var/log/daemon.log
```

**Что логирует ОС:** системные события, демоны, сетевые/дисковые сообщения, сообщения служб.
